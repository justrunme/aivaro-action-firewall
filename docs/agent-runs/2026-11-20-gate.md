## How the probe works

`gate-probe start` makes a random 16-hex nonce and the command `touch .justrunme-gate-probe-<nonce>`. The operator asks the agent, in the session to check, to run it. The hook recognises exactly that command and always denies it (category `GATE_PROBE`, reason `gate probe <nonce>`); it never allows it, so recognising it cannot weaken the gate. `gate-probe finish` then records what the workspace shows as a signed `gate_probe` receipt:

| Seen | Status | What it proves |
|---|---|---|
| a signed `hook_decision · deny · GATE_PROBE` naming the nonce, after the probe started | ACTIVE | a hook in this workspace ran for that call (the receipt names the workspace mission, not a session) |
| the file `.justrunme-gate-probe-<nonce>` exists | INACTIVE | nothing blocked the command |
| neither | UNKNOWN | no proof either way; it does not mean blocked |

ACTIVE turns UNKNOWN 15 minutes after its receipt; a recorded INACTIVE stays until the next probe. Recent hook receipts without a probe are shown for information only. The ordering policy (`justrunme verify`, rule 8) refuses an ACTIVE `gate_probe` that does not cite the hook's denial of its own nonce made after the probe started.

## Result

| Command | Kiro session | What the agent did and said | Receipts |
|---|---|---|---|
| `gate` | `JUSTRUNME_GATE=on` | ran `touch .justrunme-gate-probe-0b9cff08ae93d8e3`; Kiro showed "intercepted by PreToolUse hooks before execution"; the agent: "The command was blocked … The file was never created." | #0 `hook_decision · deny · GATE_PROBE`; #1 `gate_probe · ACTIVE` (cites #0) |
| `gate-off` | without `JUSTRUNME_GATE` | ran `touch .justrunme-gate-probe-8c71666fa7aae724`, exit 0; the agent: "The command ran successfully … the file was created in the workspace root" | #2 `gate_probe · INACTIVE`, `canary_present: true` |

Turn durations, from the script's state file: 7.7 s and 6.1 s. After the check `justrunme verify` passed for the 3 receipts, `finish` had removed the canary file, and the workspace's git tree was clean.

Limit of the method: the operator key that signs hook receipts is read from the key directory without a passphrase. In a session the gate does not cover, an agent with a shell could read it, sign a denial of the probe itself and remove the canary, and Gate Health would show ACTIVE. Gate Health finds a misconfigured or untrusted workspace; it is no defence against a hostile agent that is already ungated.

What this shows: in one session each, Gate Health told a gated Kiro CLI session from an ungated one, and both outcomes are signed. What it does not show: the gate-off case is made by leaving `JUSTRUNME_GATE` unset; the untrusted Kiro IDE workspace of `2026-11-20-ide.md` was not probed (it needs the operator in the IDE). A probe covers the session that ran the command, at that time, and only for shell calls; it says nothing about another session or about tools Kiro does not pass to the hook. One run each, not a rate.
